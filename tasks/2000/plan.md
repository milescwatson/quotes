## 1. Define the quote schema

Add `database/versions/0001/quotes/schema.sql`, a short specification, and database grants following the existing identity schema conventions. Use a `public.quotes` table:

| Field | Proposed storage | Rules |
| --- | --- | --- |
| Quote ID | `id bigint GENERATED BY DEFAULT AS IDENTITY (CACHE 1) PRIMARY KEY` | Auto-incrementing bigint identifier generated by the database. |
| Organization ID | `organization_id bigint NOT NULL` | References `organizations.id`; every quote belongs to one organization. |
| Customer ID | `customer_id integer NULL` | Numeric customer ID; defaults to `NULL`. No customer table or foreign key in this phase. |
| Customer Name | `customer_name text NOT NULL` | Required, trimmed, nonblank; maximum 120 characters. |
| Project Name | `project_name text NOT NULL` | Required, trimmed, nonblank; maximum 120 characters. |
| Quote title | Derived, not separately stored | `customer_name + ' - ' + project_name`, e.g. `Acme - Office Renovation`. Returned as `title` by the API. |
| ModifiedBy | `modified_by bigint NOT NULL` | References `users.id`; identifies the application user responsible for the last write. |
| ModifiedWhen | `modified_when timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP` | Set on initial insertion and every future update. |

Customer identifiers use numeric IDs. Planning assumptions: both names are required; the title separator is ` - `. Duplicate titles are allowed. Customer Name remains independently stored while Customer ID is blank.

Use database checks for name normalization and length, and restrictive deletion behavior for organization/user references, consistent with the identity schema. Add an organization-leading index on `(organization_id, modified_when, id)` for the default list order and pagination.

Modification metadata is server-owned: future writes must set `modified_by` from the authenticated application user and `modified_when` from database time in the same transaction. Do not rely on clients or triggers to maintain these values. Trusted development seeds must populate a valid actor and timestamp as well.

Give the API role SELECT access to quotes for this phase; keep seed writes in a separate development/operator workflow. Follow the repository's checkpointed DSQL DDL and asynchronous-index process, verifying target compatibility during implementation and before release.

## 2. Add the organization quotes list API

Add `GET /organizations/{orgId}/quotes` to the OpenAPI contract, Gateway configuration, and Lambda route handling.

- Reuse current authentication, enabled-user checks, active-organization checks, and current membership authorization. Admins, editors, and members can all view quotes in their organization.
- Scope every query to the authorized organization ID. Reject access using the existing error conventions; knowing a quote, customer, or organization ID never grants access.
- Return `{ items, page, pageSize, totalItems, totalPages }`. Each item includes `id`, `organizationId`, `customerId`, `customerName`, `projectName`, `title`, `modifiedBy`, `modifiedByName`, and `modifiedWhen`. Serialize `customerId` as a JSON number or `null`.
- Keep `modifiedBy` as the stable user ID. Resolve `modifiedByName` from the user's display name, falling back to email. Keep historical quotes visible when the modifier has left the organization or has been disabled; viewing permissions depend on the current viewer.
- Return timestamps in ISO 8601 UTC format. Derive the title consistently in the API and fixtures.
- Use simple page-number pagination: `?page=1&pageSize=50`. Default to page 1 and 50 rows; require positive integer inputs and cap page size at 100. Sort by `modified_when DESC, id DESC` and query with `LIMIT pageSize OFFSET ((page - 1) * pageSize)`.
- Count quotes within the authorized organization and return `totalPages = ceil(totalItems / pageSize)`. Read the count and page in the same transaction. An empty list has zero total pages; a page beyond the last page returns empty items with accurate totals. Apply organization authorization on every page request. Separate requests reflect current data, so later writes may move rows between pages.
- Regenerate the frontend API types and extend the existing HTTP/fixture integration. Fixtures remain explicitly development-only.

## 3. Add the Quotes list UI

Create `app/app/pages/organizations/[orgId]/quotes/index.vue` and add a **Quotes** link under the current organization in `AppShell.vue`, visible to all organization members.

Use the existing organization route helpers and request adapter so browser aliases resolve to organization IDs for the API. Retain the existing Overview page and organization-switching behavior.

The page should have a **Quotes** heading and a simple responsive table:

| Column | Display |
| --- | --- |
| Quote title | Derived customer/project title, rendered as plain text until detail pages exist. |
| Customer Name | Stored customer name. |
| Project Name | Stored project name. |
| ModifiedBy | Resolved display name or fallback email. |
| ModifiedWhen | Localized date and time, with the exact timestamp available through a semantic `time` element. |

Customer ID stays in the data contract but is omitted from the initial table because it is blank for now. Use **Previous** and **Next** controls with the current page, total pages, and total quote count. Disable controls at the boundaries and hide them for an empty list. Replace rows when changing pages. If a page request fails, retain the last successful rows and page label and allow retry. If data changes leave the requested page beyond the last page, load the new last page (or show the empty state when no quotes remain).

Reuse `PageHeading`, `ResourceState`, and the existing resource/request patterns. Include initial loading, empty ("No quotes yet."), retryable error, expired-session, and revoked-access states. Clear rows and reset to page 1 on organization changes, cancel pending requests, and discard stale responses from previous organizations or page requests.

Follow the existing Tailwind styling and accessibility conventions: semantic table headings, keyboard-accessible controls, readable long names, and a contained horizontal scroll area on narrow screens. Do not add New Quote buttons, edit actions, or row navigation until those workflows exist.

## 4. Fixtures and validation

Provide development quotes for at least two organizations, including blank Customer IDs, long names, different modifiers/timestamps, enough rows to exercise pagination, and an organization with no quotes. These fixtures support review without requiring a creation UI. Keep fixture rows out of production; use a separately documented development seed when verifying the live database/API path.

Acceptance checks:

- Schema tests accept numeric and null Customer IDs and reject invalid customer ID types, blank/untrimmed/overlong names, missing modification metadata, and invalid organization/user references.
- API tests verify title derivation, numeric/null Customer ID serialization, modifier fallback, newest-first order, stable ordering for equal timestamps, page offsets/totals, empty and out-of-range pages, invalid page numbers, and page-size limits.
- Authorization tests cover each member role, cross-organization isolation, removed memberships, disabled viewers, archived organizations, and a former member as historical modifier.
- Browser tests cover navigation, populated/empty/error states, Previous/Next boundaries and page labels, pagination retry, recovery when the last page disappears, and reset to page 1 when switching organizations while requests are pending.
- Review keyboard behavior, long content, and mobile layout. Run frontend type checking/build, API tests/build, and relevant existing regression tests.
- Before live release, verify DSQL schema/index creation, runtime grants, and the authenticated list endpoint against a development database with known seed data. Local fixture/PGlite tests alone do not establish deployed behavior.
